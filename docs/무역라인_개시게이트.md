# 무역 라인 개시 게이트 — 선커밋 틀

> **아직 열리지 않았다.** 게이트 ①이 미통과다.
> 이 문서는 게이트가 **열리는 즉시 채우기 위한 틀**이고, 지금은 비어 있는 칸이 정상이다.
> 근거: 지침 §5.0 라인 개시 게이트 5개 · 설계 v2 §5.3 착수 정지선.

## 왜 무역이 다음인가 [확정 · 설계 v2 §4]

산업 확장 순서는 **물류 → 무역 → 유통**이다. 무역이 먼저인 이유는 하나다.

**관세청 「항구·공항별 수출입실적」이 기존 인천항 시리즈와 같은 대상을 다른 소스로 본다.**
첫 무역 편이 곧 기존 7편의 최대 한계를 푸는 편이 된다 —
`report_07` §4.1 한계 ③ *「단일 소스다. 공컨테이너 물동량 API 하나에서만 가져왔다.
다른 기관 통계와의 교차 확인은 하지 않았다.」*

즉 무역 라인의 첫 편은 새 축을 여는 것이 아니라 **이미 발행한 결론을 다른 신고 체계로 대조**하는 것이다.
브랜드 이름이 하는 일 그대로다.

## 게이트 ① 소스 실재 확인 — **미통과**

```
python analysis/probe_customs.py
```

**실측 이력**

| 일시 | 항구·공항별 수출입실적 | 세관장확인대상물품 | 대조군(공컨) |
|---|---|---|---|
| 2026-08-25 | 막힘 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(30) | 막힘 (동일) | — |
| 2026-08-26 | 막힘 **HTTP 403** | 막힘 **HTTP 403** | **정상** `HTTP 200 / code=00` |

**대조군이 정상이므로 키·네트워크 문제가 아니다.** 공공데이터포털 **활용신청 승인이 선행**이다(운영자 계정 조작).

> **[미확인] 403의 원인.** 2026-08-25에 기록된 실패 신호는 `returnReasonCode=30`이었는데
> 08-26에는 **403으로 형태가 바뀌었다.** 미승인 때문인지 엔드포인트 경로 차이인지 **가르지 못했다.**
> 승인 후에도 403이면 경로부터 다시 확인한다. 추정으로 메우지 않는다.

## 게이트 ② 개시 선커밋 — **비워 둔다. 의도적이다**

답할 **질문 3개 이상** + 데이터 축 + 출처 목록.

**지금 쓰지 않는다.** 게이트 ②는 *「질문 3개가 안 나오면 라인감이 아니다」* 라는 **시험**이다.
소스를 열어 보기 전에 질문을 지어내면 **그 시험을 미리 통과시켜 버린다.**
어떤 필드가 실제로 오는지, 항만 코드가 인천을 어떻게 가리키는지, 월별 입도가 되는지 —
전부 실호출로만 알 수 있다. **소스가 세 질문을 감당하는지는 소스를 보기 전에 알 수 없다.**

정의문·소개 페이지를 근거로 질문을 쓰는 것이 사고 8이 금지한 그것이다.

| | 채울 것 | 상태 |
|---|---|---|
| 질문 1 | | ① 통과 후 |
| 질문 2 | | ① 통과 후 |
| 질문 3 | | ① 통과 후 |
| 데이터 축 | | ① 통과 후 |
| 출처 목록 | | ① 통과 후 |

**질문이 셋이 안 나오면 라인을 열지 않는다.** 그 판정도 산출물이다.

## 게이트 ③ 성공 조건 — 초안 [①·② 통과 시 확정]

**첫 편이 `report_07` 한계 ③을 실제로 푸는가.** 즉 인천항 공컨 물동량을 관세청 신고 체계로
교차 확인해, 두 소스가 **일치하는지 어긋나는지를 판정**한다.

**어긋나도 성공이다.** 「두 공식 소스가 이만큼 다르다」는 것이 발행 가치다 —
그 경우 어느 쪽이 옳은지 단정하지 않고 **차이의 크기와 그 구조적 사유(집계 체계 차이)만 적는다.**

---

## 게이트 ④ 종료 조건 — 초안 [①·② 통과 시 확정]

- **3편 발행 후에도 「1차 출처 링크 100%」·「린터 FAIL 0」을 못 맞추면 접는다.**
- **소스가 인천항을 월 단위로 분해하지 못하면 첫 편에서 접는다** — 연 단위로는 기존 시리즈와 맞댈 수 없다.
- 기한: **첫 실호출 성공일로부터 3개월.** 그 안에 1편도 못 내면 종료 판정을 내린다(지침 §1.4 2층).

---

## 게이트 ⑤ 종료 시 회수물 — 초안

- **출처표** — 관세청 API 필드 정의와 인천항 공컨 API의 대응 관계
- **결합 게이트 기록** — 단위·기간·집계 축이 어디서 어긋나는지(지침 §3-9)
- **판정 불가 사유** — 접었다면 왜 접었는지. 이것만으로도 5.B 이슈 검증 라인의 소재가 된다

## 결합 게이트 — 이 라인은 처음부터 이종 결합이다 [지침 §3-9]

두 소스를 맞대는 것이 이 라인의 전부이므로, 결합 게이트가 **선택이 아니라 기본 절차**다.

1. **단위 · 기간 · 집계 축 정합을 맞대기 전에 확인한다.**
   공컨 API는 TEU·박스 수 / 관세청은 신고 건수·중량·금액일 가능성이 높다 — **[미확인]**, 실호출로 본다.
2. **항등식은 증거가 아니다.** 두 소스의 합이 맞아떨어져도 그것은 무결성 확인이지 결론이 아니다.
3. **비정수 배율은 단위 문제가 아니라 축 불일치 신호로 취급한다.**

- 새 소스의 값은 **창(기간·모집단·단위)과 지위를 달고** 대장에 올린다
